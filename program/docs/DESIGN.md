# 設計: HTML＋Python（Flask）から HTML＋Rust（＋Python）へ（版 12.0.0）

利用者の決めたこと（2026-10-26）:
- Flask なしで動くよう Rust に置き換え、HTML＋Rust＋（Python）にする
- 読み込みや処理に時間がかかるので、並列・高速化・裏の処理で、安定して速くロットデータを読み込み処理する
- 起動は exe から。配布の版の作り方・配布の仕組み・更新の仕組みは、別リポジトリ LotScope を参考にする

この文書は「なぜ・どう分けたか・何で確かめたか」を残す。

## 1. 役割の分け方

| 受け持つもの | 何を | 理由 |
|---|---|---|
| **Rust**（`desktop/`・Tauri。exe） | 窓・起動と終了・1 つだけ起動・画面の配信・**アプリの中身のすべて**（CM3 の取得と整形・台帳の写しと突合せ・列の設定・HOT コイル作業順・CSV・Excel）・配布と更新・ショートカット | 利用者の PC に Python を入れなくてよい（入口は exe だけ）。台帳の読み込みのように重い所を速く・並列にできる |
| **画面**（`program/app/web`） | 旧版と同じ HTML/JS/CSS。問い合わせは `fetch("/api/...")` のまま | 見た目と使い方を変えない（移す前と後を撮って比べ、違いは時刻とパスだけ） |
| **Python**（`program/tools`・`desktop/bundle`） | 開発の道具だけ: 作り物のデータ・作り物の CM3・旧版の答えの記録・撮影と採点・配る ZIP の組み立て・通しの確かめ・アイコンの描画 | 利用者の PC では使わない |

LotScope は業務の処理を Python（標準入出力でつないだ中身）に残したが、このアプリは中身が小さく（旧版で約 1,500 行）、
Python を各 PC に入れる手間（Microsoft Store 版の扱い・本物の PID の見張りなど）の方が大きいので、中身もすべて Rust に移した。

## 2. つなぎ方（ポートなし）

```
 WebView2（画面）
   │ fetch("/api/...")  … 置き場は http://sv.localhost/（Windows）・sv://localhost/（ほか）
   ▼
 Rust: 自前の仕組み "sv"（desktop/src/main.rs）。1 つの問い合わせを 1 本の糸で答える（CM3 を待つ問い合わせがほかを待たせない）
   ├─ /__desktop/…   → 窓が答える（版・更新・ショートカット・配布・保存の記録・自己診断）
   └─ それ以外        → アプリの中身（desktop/src/app.rs の App::handle。旧版の Flask の道と同じ）
```

開発で画面だけをブラウザから見るときは、同じ `App::handle` を小さな HTTP で出す（`desktop/examples/serve.rs`。配る exe は HTTP を開かない）。

## 3. 移した物と、答えをそろえる決まり

| 旧版（Python） | Rust | そろえ方 |
|---|---|---|
| `cm3_client.py` | `cm3.rs`・`text.rs` | 行の区分・停止の文言（応答の項目の順。`serde_json` の preserve_order）・日付の補い・文字化けの直し（latin-1／cp1252 → UTF-8／CP932） |
| `master.py` | `master.rs` | 列名と値のそろえ方（NFKC・数は数）・ロット番号の列の自動判定・キーの組・重複 |
| `app.py`（列の設定・配色・HOT・API） | `app.rs`・`view.rs` | 道・答えの形・誤りの文言。JSON の鍵は名前の順（Flask の jsonify と同じ。画面の変換表の並びが変わらない） |
| `xlsx_writer.py` | `xlsx.rs` | XML を一字一句同じに |
| Python の書き方 | `pyfmt.rs` | 小数の repr（`1e+16`・`1e-05`）・`float()`・`round()`・SQLite の値の `str()` |

## 4. 速さ（ロットデータの読み込み）

作り物の台帳（列 113・本物と同じ全列 TEXT）とスケジュール（1 設備 70〜80 行）で、旧版と同じ手順を測った（`cargo run --release --example bench`・
旧版は同じ手順の Python。CM3 は 1 設備あたり 1 秒かかる作り物）。Linux・4 コア。

| 測った物 | 旧版（Python）6,881 行 | Rust 6,881 行 | 旧版 10 万行 | Rust 10 万行 |
|---|---|---|---|---|
| 台帳の初めの読み込み（写し＋検査＋読み込み） | 1.59 秒 | **0.11 秒** | 13.9 秒 | **0.69 秒** |
| 台帳の読み直し | 1.71 秒 | **0.11 秒** | 15.0 秒 | **0.77 秒** |
| HOT コイル作業順（3 設備を取りに行く） | 3.10 秒 | **1.01 秒** | 3.14 秒 | **1.01 秒** |
| 台帳設定の画面（ロット番号の列の候補） | 0.95 秒 | **0.03 秒** | 1.06 秒 | **0.13 秒** |
| 列の設定の実データ（台帳の全列） | 0.006 秒 | 0.010 秒 | 1.03 秒 | **0.007 秒** |
| 読み込み中に一覧を開く | 読み込みが終わるまで待つ（錠） | **2 ミリ秒**（前の台帳で答える） | 同 | **3 ミリ秒** |
| メモリ（最大） | 197 MB | **42 MB** | 2,335 MB | **325 MB** |

効いた作り:
- **裏の糸**（`master.rs` の `spawn`）: 共有から写す・読み込むのは問い合わせの外。読み終えた控え（`Snapshot`）を丸ごと差し替えるので、
  読み込み中も一覧は止まらない。起動の直後は、共有を見に行く前に前回の手元の写しを読む（共有が遅くても、すぐ台帳が付く）。画面は台帳を読み込み中なら少し待って読み直す
- **並列**: 大きな表（2 万行超）は rowid の範囲で分け、糸ごとに別の接続で読んで rowid の順につなぐ（10 万行で 1.24 秒 → 0.39 秒）。
  ロット番号の列の判定は列ごとに糸を分ける。HOT は 3 設備を同時に取りに行く（待ちはいちばん遅い設備の分だけ）
- **軽い行**: 1 行を 1 つの文字列と区切りの位置で持つ（セルごとに文字列を作らない）。キーを変えたときは行を分け合い、索引だけ作り直す
- 同じ設備を同時に取りに行かない（先に取りに行った答えを待って使う）

## 5. 配布と更新（LotScope と同じ仕組み）

LotScope の `release.rs`・`update.rs`・`distribute.rs`・`install.rs`・`lnk.rs`・`proc.rs` を写し、配る形の目印を `program/app/brand.json` にした
（LotScope は `program/sidecar.py`）。置き場の形・版の比べ方・取り込みの確かめ（指紋・危ない名前・1 GB・版の一致）・入れ替えと戻し・
配る版（`distribute.json`）・配る入口・ショートカット（作業フォルダも app・消された物は作り直さない）はそのまま。

| 違い | 理由 |
|---|---|
| 更新の置き場は `config.json` の `update.source`（LotScope は参照先の共有マスタ） | 中身に尋ねる必要が無い。**初めて共有から開いたときから**置き場を確かめるので、新しい版に 1 回早く届く |
| 版を置ける人は、置き場に書ける人（LotScope は権限の表） | 権限の仕組みを持たない小さなアプリ。共有フォルダの権限で決まる |
| 「開けなかった版」は、設定か画面が読めない版（LotScope は Python の中身が起動できない版） | 中身が exe の中にあるので |
| マスタの置き場・推奨の札・名前の歴史の作業場所の移し替えは持たない | このアプリには無い仕組み |

評価関数: Rust の単体（取り込み → 入れ替え → 戻し・危ない ZIP・起動の最初の確かめ・配る版の向き・ショートカット・配布の置く／配る／消す／入口から新しい PC）と、
本物の窓での通し `desktop/bundle/verify.py update`（24 項目: 共有から写る・起動の最初に取り込む・閉じている間に置いた版に 1 回の起動で入れ替わる・
開けない版を控えへ戻す・配る版を戻す・新しい PC が入口から入る・共有のファイルは 1 つも変わらない）。Linux（WebKitGTK）で 24/24。Windows は CI。

版の作り方: `program/app/version.py`（版・更新履歴・RELEASE）＝ exe の版（`Cargo.toml`・`tauri.conf.json`）。`app_build.py --release` が配る物の中身の要約を記録し、
`tests/test_version.py` が版の上げ忘れを止める。main に入ると CI（`desktop.yml`）が Windows で作って自己診断・通しを流し、Releases に ZIP・指紋・release.json を載せる。

## 8. 分からないこと・使う前に確かめること

- 依頼の「画像ファイルの読み込みや処理」: このリポジトリには画像ファイルを読む処理が無かった。時間がかかっていたのは台帳（LOTNOW.sqlite3）の写しと読み込み・CM3 の取得なので、
  そこを速くした。画像の処理が別にあるなら、どの処理かを教えてもらう必要がある
- 本物の台帳の大きさと、共有フォルダからの写しの速さ（作り物の 7 千行・10 万行で測った）
- `use_system_proxy: true` のとき: 旧版の Python は Windows のプロキシの設定（レジストリ）も読んだが、Rust は環境変数（HTTP_PROXY など）だけを読む。既定は `false`（直接つなぐ）なので、既定のままなら違いは無い
- 設定の置き場: 旧版は `app` フォルダ（共有から動かしていれば全員で同じ）に保存していた。新しい版は既定で PC ごと（作業場所の `settings`）。全員で同じ設定にするなら `settings_dir` に共有のフォルダを書く
- 更新の置き場（`update.source`）はまだ空。配る共有フォルダを決めて書く必要がある
